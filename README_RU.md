# TupoNVR

[English version](README.md)

Лёгкий self-hosted NVR для RTSP камер. Один контейнер приложения (FastAPI, SQLite, React, FFmpeg) и один MediaMTX. Запись не зависит от открытых вкладок. Детекции, транскодирования, брокеров и отдельных контейнеров камер нет.

## Быстрый старт

```sh
git clone <URL-этого-репозитория> TupoNVR
cd TupoNVR
cp .env.example .env
# Для просмотра с другого устройства укажите LAN IP хоста в WEBRTC_HOST.
# Для постоянной записи укажите нужный путь в DEFAULT_RECORDING_PATH.
docker compose up -d --build
```

Откройте `http://<адрес-хоста>:8080`, перейдите в **Камеры**, добавьте основной RTSP URL. Включённая запись запускается автоматически. На локальном компьютере значение `WEBRTC_HOST=127.0.0.1` работает без дополнительных правок; для просмотра по сети замените его на адрес хоста, доступный браузеру. Откройте на firewall TCP 8080/8889 и UDP 8189 в пределах LAN. Порты меняются через `.env`.

> Здесь нет удалённого Git-репозитория, поэтому строка `git clone` станет рабочей после публикации проекта пользователем. Передайте каталог в свой Git и используйте его URL.

## Видеотракт

```text
RTSP камера ── один upstream ── MediaMTX ── WebRTC/WHEP ── браузер
                                  │
                                  └── локальный RTSP ── FFmpeg -c:v copy ── MP4 сегменты
```

Для substream MediaMTX создаёт отдельный путь и подключается к камере только при наличии зрителей multiview. Основной поток постоянно подключён, если запись разрешена расписанием и хранилище готово; иначе подключается по запросу. Каждый viewer получает свою WebRTC сессию, но MediaMTX переиспользует исходный RTSP upstream. React использует официальный `reader.js` MediaMTX (см. `frontend/public/MEDIAMTX-LICENSE.txt`); плитки переключают `contain`/`cover` в браузере без ресайза на сервере. Разметка мультиэкрана сохраняется и допускает любое число колонок до 12, перенос и изменение размеров плиток.

FFmpeg пишет видеодорожку без декодирования (`-c:v copy`), аудио в MVP не записывается. Каждый процесс принадлежит одному `ProcessSupervisor`; нет shell-интерполяции. На штатном завершении FFmpeg получает SIGINT и до 15 секунд на финализацию MP4, затем SIGKILL. Перезапуск при аварии имеет экспоненциальную задержку 2–60 секунд. При смене часа UTC процесс штатно ротируется. MediaMTX восстанавливает соединение с источником самостоятельно.

Записи располагаются как `<storage>/<destination>/<camera_id>/YYYY/MM/DD/HH/YYYYMMDDTHHMMSS.mp4` (UTC). Один сегмент по умолчанию около 10 минут; граница зависит от ключевых кадров камеры. Архив показывает только сегменты с корректным MP4, проверенные `ffprobe`. Просмотр/скачивание обслуживает FastAPI. Браузер воспроизводит MP4 только при поддерживаемом видеокодеке.

## Хранилище и срок хранения

`DEFAULT_RECORDING_PATH` в `.env` — путь **на хосте**, привязанный к `/recordings` контейнера. Это может быть локальный диск или заранее смонтированный NFS/SMB каталог. Например:

```sh
sudo mount -t nfs nas:/export/nvr /srv/nvr
# Затем DEFAULT_RECORDING_PATH=/srv/nvr в .env
```

`recording_destination` камеры — имя подкаталога, например `default` или `garage`; абсолютные пути и `..` не принимаются. Можно монтировать отдельный файловый ресурс внутрь такого каталога на хосте. Монтирование, права записи и восстановление mount после загрузки ОС настраиваются на хосте. Проверьте их до включения записи, а также поведение при недоступности NFS/SMB.

Retention: число дней 1–3650; пустое значение означает без ограничения по возрасту. Сегменты удалённой камеры хранятся 7 дней. Раз в 5 минут воркер индексирует записи и удаляет старые сегменты; при нехватке свободного места удаляет самые старые учтённые файлы до достижения `MIN_FREE_SPACE_GB`. Текущий час активной камеры защищён от удаления. При полном диске, занятом только активными сегментами, резерв не гарантирован: настройте разумный объём и retention, мониторьте `/metrics`. Удаление сегмента вручную происходит через API. SQLite использует WAL; метаданные удалённых файлов очищаются воркером. ID камер не переиспользуются после удаления; при первом запуске старой базы схема автоматически обновляется с сохранением строк и учётом существующего архива и layout.

## Конфигурация

| Переменная | По умолчанию | Назначение |
|---|---:|---|
| `NVR_PORT` | `8080` | Порт веб-приложения на хосте |
| `WEBRTC_PORT` | `8889` | HTTP signaling WHEP |
| `WEBRTC_UDP_PORT` | `8189` | UDP медиа WebRTC |
| `WEBRTC_HOST` | `127.0.0.1` | IP/DNS хоста для ICE; укажите LAN IP для других устройств |
| `DATA_DIR` | `./data` | SQLite на хосте |
| `DEFAULT_RECORDING_PATH` | `./recordings` | Корень видео на хосте |
| `SEGMENT_SECONDS` | `600` | Целевая длина сегмента |
| `MIN_FREE_SPACE_GB` | `5` | Резерв места |
| `AUTH_USERNAME`, `AUTH_PASSWORD` | пусто | Опциональный вход в UI/API; заполните оба |
| `COOKIE_SECURE` | `false` | Secure session cookie; включите при HTTPS доступе к UI |
| `LOG_LEVEL` | `INFO` | Уровень логирования |
| `DEFAULT_LANGUAGE` | `en` | Начальный язык интерфейса: `en` или `ru` |
| `WEBHOOK_URL` | пусто | Generic HTTP(S) endpoint; пусто отключает уведомления |
| `WEBHOOK_TOKEN` | пусто | Необязательный Bearer token |
| `WEBHOOK_DEBOUNCE_SECONDS` | `60` | Непрерывная неисправность до первого события |
| `WEBHOOK_COOLDOWN_SECONDS` | `600` | Минимальный интервал между новыми incident-событиями одного объекта |

Браузерные запросы изменения состояния проверяют Origin: reverse proxy должен сохранять исходный Host. Для HTTPS задайте `COOKIE_SECURE=true`.

У приложения один процесс Uvicorn (`--workers 1`): второй worker мог бы запустить второй FFmpeg на камеру. База содержит пароли камер в открытом виде; защищайте каталог `DATA_DIR` и резервные копии. SQLite файл создаётся с правами `0600`. Структурированные события backend не содержат URL/паролей; access log Uvicorn отключён. Не публикуйте MediaMTX и NVR в интернет напрямую. **Опциональная авторизация защищает UI/API и файлы архива, но не прямой WebRTC порт MediaMTX**: ограничьте 8889/8189 firewall или добавьте отдельный защищённый reverse proxy, если этот порт не должен быть доступен всем в LAN. Для HTTPS прокси требуется настроить HTTPS на WHEP endpoint отдельно, иначе браузер заблокирует mixed content.

## Интерфейс и API

- **Обзор:** число камер, онлайн, запись, свободное место, ошибки. «Смотреть» открывает `/cameras/<id>/live` с основным потоком одной камеры. Обновление страницы и навигация браузера сохраняют выбор; настройки мультиэкрана независимы.
- **Камеры:** добавить, изменить, отключить, проверить, удалить. Пустой пароль или RTSP URL при редактировании сохраняет старое значение; substream удаляется отдельным переключателем. В списке URL скрывает путь и параметры, которые могут содержать секреты.
- **Мультиэкран:** добавить камеру, перетащить заголовок, изменить размер за угол, выбрать `contain`/`cover`; отдельный просмотр открывает основной поток.
- **Архив:** дата и время в часовом поясе устройства; одна, несколько или все камеры на общей шкале времени с пробелами, синхронное воспроизведение, скорость, фокус, соседние сегменты и скачивание. Переходы между файлами и возврат после пробелов выполняются отдельно для каждой камеры.
- **Хранилище:** доступность, возможность записи, резерв места и защита каждого destination; состояние очереди webhook.

OpenAPI: `/docs`; основные маршруты: `GET/POST /api/cameras`, `GET/PUT/DELETE /api/cameras/{id}`, `POST /api/cameras/{id}/start|stop|check`, `GET /api/cameras/{id}/status`, `GET /api/recordings?camera_id=&date=YYYY-MM-DD&limit=&offset=`, `GET /api/recordings/{id}`, `GET /api/recordings/{id}/download`, `DELETE /api/recordings/{id}`, `GET/PUT /api/layout`, `GET /api/dashboard`, `GET /api/storage/status`, `GET /api/storage/destinations`, `PUT /api/storage/destinations/{name}`, `GET /api/notifications/status`, `GET /api/recordings/timeline?camera_id=&start=&end=`, `GET /api/recordings/at?camera_id=&time=`, `GET /api/recordings/{id}/adjacent?direction=next|previous`, `GET /health`, `GET /ready`, `GET /metrics`. Если включена авторизация, `POST /api/login` создаёт HttpOnly session cookie; для CLI поддерживается Basic auth.

## Диагностика

```sh
docker compose ps
docker compose logs --tail=100 nvr-app
docker compose logs --tail=100 mediamtx
curl http://localhost:8080/health
curl http://localhost:8080/ready
```

- **ONLINE, но нет видео:** проверьте кодек камеры. H.264 наиболее совместим с браузерами; H.265 поддерживается не всеми. Проверьте `WEBRTC_HOST`, UDP 8189, TCP 8889 и консоль браузера.
- **Нет записи:** проверьте mount, права каталога и свободное место; основной RTSP путь доступен MediaMTX? Ошибки FFmpeg отражаются в статусе без вывода приватных URL.
- **Архив пуст:** текущий пишущийся сегмент не индексируется; дождитесь окончания сегмента и очередной проверки (до 5 минут), либо штатно остановите камеру. Битые после аварии MP4 не попадут в архив.
- **Изменили порт WebRTC:** перезапустите Compose. UI получает порт из backend runtime config.
- **RTSP нестабилен:** MediaMTX повторно подключается, FFmpeg перезапускается с backoff. Число процессов: один FFmpeg на записываемую камеру.

## Разработка и проверки

Требуются Python 3.12+, Node 22+, FFmpeg/ffprobe и база часовых поясов ОС (tzdata).

```sh
python3 -m venv .venv
.venv/bin/pip install -r backend/requirements-dev.txt
npm ci --prefix frontend
scripts/validate.sh
```

Одна команда выполняет `pip check`, Ruff (правила F для ошибок Python), тесты reader.js, строгую проверку TypeScript, Vite build и pytest. В репозитории нет установленного стандарта форматирования; массовое переформатирование не выполняется. `NVR_PYTHON` позволяет выбрать другой Python. Тесты изолируют SQLite и видео в временных каталогах. Integration/browser тесты по умолчанию пропускаются, а в CI выполняются обязательно:

```sh
# Скачайте официальный MediaMTX 1.21.1 для своей ОС, распакуйте его.
.venv/bin/python -m playwright install chromium
NVR_MEDIAMTX_BIN=/absolute/path/to/mediamtx NVR_RUN_BROWSER=1 scripts/validate.sh
# Можно использовать установленный Chrome через NVR_CHROME_EXECUTABLE.
```

Integration тесту нужен свободный localhost:8554; остальные порты выбираются автоматически. Он запускает синтетическую H.264 RTSP камеру, MediaMTX и приложение; проверяет прогресс FFmpeg, активную диагностику, потерю/возврат ID хранилища, остановку/возобновление по расписанию, финализацию и индексирование MP4, скачивание и HTTP Range. Browser тест проверяет реальные собранные React assets в Chromium с детерминированными API fixtures: вход, редактор расписаний, ID хранилища, диагностику, страницы архива, UTC seek, автоматический переход через полночь и пробел, сохранение layout при polling. Reader.js проверяется отдельно.

`.github/workflows/ci.yml` выполняет эти проверки на Python 3.12 / Node 22, проверяет checksum скачанного MediaMTX, собирает Docker image и проверяет HTTP `/health`, статические assets и миграцию SQLite в контейнере. CI ничего не публикует и не развёртывает. Многомесячный soak test на реальных камерах и NFS/SMB не проводился.

## Текущие ограничения

Нет аудиозаписи, детекции, PTZ, ONVIF, нескольких пользователей, фоновой перекодировки и нативного мобильного приложения. FPS/bitrate API не рассчитывает: `bytes_received` берутся из MediaMTX, что не требует декодирования. Нет автоматического ремонта повреждённого MP4, появившегося при внезапном отключении питания; SQLite и каталог с видео нужно резервировать независимо. Прямой WebRTC endpoint доступен в LAN без UI авторизации. Размер базы и каталога контролируется retention, но при `unlimited` нужен внешний мониторинг свободного места.

## Здоровье записи и проверка камеры

Доступность камеры и запись показываются двумя отдельными индикаторами в обзоре и списке камер (EN/RU). **Online** зелёный, **Offline** красный; намеренная пауза, пауза по расписанию и выключенная камера нейтральные. STARTING/RECONNECTING — предупреждение, STALLED/STORAGE_UNAVAILABLE — ошибка. Старые ошибки остановленного рекордера не показываются как активные инциденты. При паузе вместо давнего прогресса показывается «Нет активной записи».

`GET /api/cameras/{id}/status` возвращает `state` и `connectivity_state` для доступности (ONLINE/OFFLINE/UNKNOWN/DISABLED), `online` (true/false/null), `connectivity_checked_at`, `connectivity_last_success`. UNKNOWN означает начальную или устаревшую проверку, DISABLED — выключенную целиком камеру; оба состояния нейтральные. Отдельно доступны `recording_enabled` (настройка), `recording_expected` (с учётом расписания), `recording_health`, `recorder_running`, `last_progress_at`, `progress_age_seconds` и `latest_segment`. `camera_online` в /metrics равен 1/0, а при неизвестном состоянии или выключенной камере — NaN. Живой процесс FFmpeg без растущего frame/out_time_us не считается WRITING: после 30 секунд это STALLED. Здоровье и кеш проверок хранятся только в памяти, не в SQLite.

Один backend worker проверяет **основной настроенный RTSP источник напрямую** через ffprobe, независимо от записи, зрителей и MediaMTX. Проверка читает видеометаданные с кодеком и положительным разрешением, без транскодирования, с ограниченными probesize/analyzeduration и общим таймаутом 10 секунд. Одновременно работают не более двух проверок. Обычный интервал — 60 секунд после завершения; первая ошибка вызывает повтор через 15 секунд, две последовательные ошибки дают Offline. Успех сразу восстанавливает Online. До подтверждения ошибки сохраняется предыдущий результат, а данные старше 180 секунд становятся UNKNOWN. Worker проверяет очередь каждые 5 секунд; задержки также зависят от количества камер и времени ответа. Полностью выключенные камеры периодически не проверяются. Изменение источника или credentials сбрасывает кеш.

Кнопка **Проверить** использует тот же probe и может проверить выключенную камеру; параллельные запросы объединяются, результаты повторно используются в течение 10 секунд. Проверка выключенной камеры завершается до очистки кеша; изменение источника во время проверки возвращает HTTP 409 с просьбой повторить её. Опрос UI/API не запускает probes. MediaMTX sourceOnDemand сохраняется, новые временные пути для диагностики не создаются. Каждой камере нужна возможность кратковременно принять дополнительную RTSP сессию: камеры с жёстким лимитом подключений могут отклонять такую проверку. Результат — снимок доступности, не непрерывная гарантия и не тест воспроизведения WebRTC/ICE/firewall. H.264 помечается как вероятно совместимый с браузером. Сырые сообщения камеры и stderr отбрасываются; URL, credentials и пароли не попадают в логи, метрики, UI и API ошибки.

## Защита отдельного хранилища

Каждый destination проверяется отдельно: доступность, свободное место на его filesystem, реальная запись/fsync временного файла и запас `MIN_FREE_SPACE_GB`. При недоступности, отсутствии прав или резерва запись этой группы камер останавливается и возобновляется после восстановления. Другие destinations продолжают работать. Ошибка хранилища не выключает live viewing. Проверки запускаются примерно каждые 5 секунд в ограниченных subprocesses, с таймаутом 3 секунды; устаревший статус не считается готовым. Архивные метаданные недоступного destination не удаляются как «пропавшие файлы».

Для внешнего mount включите проверку идентичности **до включения записи камер**:

1. Смонтируйте ресурс на хосте внутри `DEFAULT_RECORDING_PATH`, например `/srv/nvr/nas`; настройте права записи и автоподключение после загрузки.
2. В **Хранилище** нажмите **Создать ID защиты**. Приложение создаёт случайный 256-битный ID, атомарно публикует `.nvr-storage-id` без перезаписи и проверяет чтение. Destination должен уже существовать: операция не создаёт каталог вместо отсутствующего mount. Если он не виден как отдельная точка монтирования, требуется явное подтверждение намеренно локального хранилища. Не подтверждайте это для отсутствующего внешнего ресурса.
3. Если ID уже существует, нажмите **Использовать существующий ID**. При несовпадении ожидаемого ID требуется явное подтверждение принятия ID подключённого ресурса. Создание никогда не заменяет существующий файл или уже настроенный ожидаемый ID. Невалидный файл нужно исправить вручную на нужном ресурсе. Если filesystem не поддерживает hard links/fsync, автоматическое создание завершается ошибкой; ручная настройка остаётся доступной.
4. В **Ручная настройка** можно задать свой ID: создайте `.nvr-storage-id` на самом ресурсе с содержимым 1–128 символов (латинские буквы, цифры, `_`, `-`), затем сохраните ожидаемый ID. Изменение/отключение защиты требует подтверждения в UI. API `PUT /api/storage/destinations/nas` с `{"expected_marker":"nas-primary-01"}` сохраняется. Новый API `POST /api/storage/destinations/{name}/protection` принимает `action` (`create`/`use_existing`), `previous_expected_marker` (текущее значение, включая null), `replace_existing` (явное принятие несовпадающего ID) и `allow_local` (явное разрешение создания на локальном destination). Действия работают только для настроенных destinations и используют существующий bounded subprocess, таймаут 3 секунды, безопасные сообщения и защиту от symlinks/смены каталога. При сбое после создания ID файл может остаться: используйте его существующий ID после проверки ресурса.
5. Убедитесь, что destination готов, затем включите запись. Если destination ещё отсутствует в списке, зарегистрируйте его API ручной настройки или добавьте выключенную камеру с этим destination.

Если mount исчез, ID отсутствует или не совпадает, NVR не создаёт защищённый каталог/ID и не начинает запись в подлежащий локальный каталог. `{"expected_marker":null}` отключает защиту; обычные локальные destinations, включая `default`, сохраняют автоматическое создание каталога. ID — проверка идентичности, не секрет и не замена OS mount. При потере ресурса уже открытые файловые дескрипторы остаются под управлением ОС; NVR не гарантирует сохранность текущего сегмента и не может устранить зависшие kernel I/O на NFS/SMB. Для вложенных host mounts настройте соответствующие bind mounts в Compose и проверьте их видимость внутри контейнера; NVR не управляет mount propagation.

## Редактирование камеры

Редактор загружает сохранённые поля через защищённый `GET /api/cameras/{id}/edit`: URL с полным путём без userinfo, логин, substream и остальные настройки. Пароль остаётся пустым и никогда не возвращается. Все query options URL скрыты, поскольку могут содержать vendor tokens; без новых query options они сохраняются при изменении URL. Подменённый query заменяет старый целиком. Встроенные credentials сохраняются при редактировании безопасного URL без изменения логина/пароля. Заданный новый пароль заменяет старый, пустой сохраняет. Новый логин сохраняет старый пароль; пустой логин снимает URL userinfo. Эти правила не требуют миграции базы. Обзор и общий список по-прежнему показывают сокращённый URL.

Форма сохраняет только изменённые поля через `PATCH /api/cameras/{id}`. Пропущенные поля остаются без изменений; `substream_url:null` явно удаляет substream. `PUT` также допускает частичное обновление, сохраняя прежнее поведение пустых URL/пароля и `clear_substream`. Create API не меняется. Validation errors не включают исходный запрос, чтобы не возвращать passwords/tokens.

## Недельное расписание

В редакторе камеры включите **Ограничить время записи**, настройте часовой пояс устройства на странице **Обзор** и задайте 1–14 окон с днями недели и временем. По умолчанию расписания нет — запись постоянная. `enabled` и `recording_enabled` остаются главными выключателями; расписание не включает выключенную камеру и не ограничивает live viewing.

API принимает, например:

```json
{"timezone":"Europe/Moscow","windows":[{"days":[0,1,2,3,4],"start":"22:00","end":"06:00"}]}
```

Это значение поля `recording_schedule` в существующем запросе создания/обновления камеры. Поле `timezone` сохраняется для совместимости старых клиентов; фактические окна всех камер используют единый часовой пояс устройства, а не этот индивидуальный параметр. Дни 0–6 означают Пн–Вс и относятся к началу окна; конец раньше начала означает переход через полночь, включая Вс→Пн. Начало включено, конец исключён. Полные сутки задаются `00:00`→`24:00`; одинаковые времена отклоняются. При DST используется местное время: повторяющийся осенью час проходит дважды, отсутствующий весной час пропускается. Границы применяются ближайшим sync (обычно до 5 секунд), затем FFmpeg получает до 15 секунд на финализацию. Завершённые файлы остаются в архиве. `null` убирает расписание; старые API clients, не передавшие это поле при обновлении, сохраняют существующее расписание.

## Generic webhook

Настройте `WEBHOOK_URL` (HTTP(S)) и при необходимости `WEBHOOK_TOKEN`, перезапустите приложение. Провайдеров и дополнительных сервисов нет. Неисправность ожидаемой записи или её хранилища должна непрерывно длиться `WEBHOOK_DEBOUNCE_SECONDS`; одна непрерывная неисправность вызывает одно событие. После восстановления идёт `recovery`; выключение записи или уход за границу расписания закрывает incident как `resolved`. Следующий incident ограничивается `WEBHOOK_COOLDOWN_SECONDS`. Для общей ошибки destination отправляется storage событие, а camera события подавляются, чтобы не создавать лавину одинаковых сообщений.

Пример JSON POST:

```json
{"id":"stable-event-uuid","kind":"recording","camera_id":1,"destination":"nas","reason":"stalled","state":"failure","occurred_at":"2026-10-06T09:00:00+00:00"}
```

У storage события нет `camera_id`. Payload не содержит имён камер, URL, паролей, файловых путей или сырых ошибок. Заголовок `X-NVR-Event-ID` повторяет `id`; при token добавляется `Authorization: Bearer ...`. Endpoint и token не показываются в UI/логах. Используйте HTTPS вне доверенной локальной сети. Redirects не выполняются, proxy environment не используется.

Очередь и debounce-состояния сохраняются в существующей SQLite. Доставка не блокирует запись: отдельная coroutine, timeout 5 секунд, до 3 попыток с паузами 10/20 секунд; принимается только успешный HTTP ответ. События идут FIFO, но окончательно недоставленное failure не блокирует recovery бесконечно. Получатель должен дедуплицировать по `id`: при перезапуске возможны повторные POST. Очередь ограничена 1000 ожидающими событиями; завершённые/недоставленные события очищаются через 7 дней. Состояние доставки видно в **Хранилище** и `/api/notifications/status`. Изменение URL перенаправляет накопленную очередь на новый endpoint; пустой URL приостанавливает доставку и наблюдение. Это механизм уведомлений работающего NVR; он не сообщает о полном выключении сервера и не является бессрочным журналом инцидентов.

## Поиск времени в архиве

Шкала строится по завершённым индексированным сегментам и показывает объединённые интервалы и пробелы. Переход по времени выбирает файл этой камеры и смещение внутри него; в пробеле предыдущий просмотр закрывается. Даты и времена интерфейса используют единый часовой пояс устройства; абсолютные запросы и метки записей остаются UTC. Список включает сегменты, пересекающие выбранный местный день, включая переход через полночь. Автопереход читает следующий сегмент через API, поэтому не ограничен загруженной страницей или выбранным днём; перекрывающиеся части пропускаются. Ошибка файла/кодека останавливает автоматическую цепочку, запись не перекодируется.

Timeline API требует timestamps с `Z` или timezone offset, диапазон до 31 дня и до 5000 сегментов; при превышении нужно сократить диапазон. Список загружает по 200 записей с **Загрузить ещё**. Lookup/adjacent используют существующую SQLite и её индекс камеры/времени; новая база или медиа-сервис не требуются.


## Interface language / Язык интерфейса

The interface supports English and Russian. English is the default, regardless of the browser language. Set `DEFAULT_LANGUAGE=en` or `DEFAULT_LANGUAGE=ru` in `.env` and recreate the application container (`docker compose up -d --build`) to change the initial language. Other values fail startup with a clear configuration error.

The **Language / Язык** selector is available before login and on every page. Its selection takes effect immediately and is remembered in this browser's local storage; it overrides the server default. Switching languages preserves forms, layout, archive selection and playback. Dates are formatted for the selected language in the installation timezone. If browser storage is disabled, switching still works for the current visit; the next visit uses the server default. Remove the `nvr-language` local-storage key to use the server default again.

`GET /api/language` returns only `{"default_language":"en"}` (or `ru`) and is available without authentication so that login can use the configured language. The normal application configuration and camera/storage APIs retain their authentication requirements.

Интерфейс поддерживает английский и русский; по умолчанию используется английский. `DEFAULT_LANGUAGE=ru` задаёт русский для первого посещения. Переключатель **Language / Язык** доступен до входа и сохраняет выбор в этом браузере. Этот выбор имеет приоритет над серверной настройкой. Переключение не сбрасывает формы, раскладку или просмотр архива; время архива использует часовой пояс устройства.


## Installation timezone and synchronized archive

Set the installation timezone on **Overview → Appliance time**. `APP_TIMEZONE=UTC` is the initial default; a UI-saved preference overrides it and persists as `/data/settings.json` on the existing data volume. There is no database migration. Existing recording timestamps, filenames, logs and webhook payloads remain UTC. **Existing per-camera schedule timezone fields are retained for compatibility but every schedule now uses the installation timezone:** configure it before relying on schedules after upgrading.

Archive supports one, several or all cameras on one absolute playback clock, with aligned availability tracks, shared play/pause/seek/speed, automatic independent segment transitions, gap recovery, and individual-camera fullscreen. Local archive dates use their true DST-aware day bounds; repeated local times require an offset choice and nonexistent times produce an error. Browser timezone does not decide the query instant. No transcoding or media composition is added.

See [time model, configuration, APIs, synchronization strategy and limits](docs/time-and-archive.md).
