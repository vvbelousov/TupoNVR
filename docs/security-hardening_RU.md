# Аутентификация и безопасность видео

[Документация](README_RU.md) · [English](security-hardening.md)

Для совместного использования задайте `AUTH_USERNAME` и `AUTH_PASSWORD`. Оба пустых значения отключают вход; неполная пара вызывает ошибку запуска. Предпочитайте доверенную LAN или VPN, для удалённого доступа используйте HTTPS. См. [сетевые режимы и открытые порты](networking_RU.md).

## Результаты аудита и исправления

Ранее детерминированная подписанная cookie работала после выхода, а два входа в одну секунду создавали одинаковую cookie. Теперь случайные сессии хранятся на сервере, отзываются отдельно, имеют абсолютный срок 24 часа и привязаны к учётным данным. Истёкшие/отозванные cookie дают обычный 401 без запроса браузерной Basic Auth. Cookie имеют HttpOnly, SameSite=Strict и необязательный Secure. Изменяющие запросы проверяют Origin, включая схему, и отклоняют cross-site fetch; небраузерные клиенты без Origin продолжают работать.

Ранее опубликованный TCP 8889 позволял смотреть WHEP без аутентификации FastAPI. Теперь OPTIONS/POST/PATCH/DELETE браузера проходят через `/api/media`: проверяются сессии приложения, разрешены только пути просмотра камер, каждый ресурс WHEP привязан к создавшей его сессии. Прокси передаёт SDP, ICE links и ETags, переписывает Location, ограничивает размер запросов и убирает Basic Auth challenges. При выходе запрашивается удаление активных ресурсов; очистка истёкших сессий выполняется каждые пять секунд и повторяет неудачные удаления. При запуске приложение удаляет оставшиеся WebRTC-сессии.

Получение видео камер не изменено: MediaMTX читает настроенные RTSP URL с учётными данными камер. FFmpeg получает поток через приватный relay. Приложение управляет приватным API MediaMTX. HLS, RTMP, SRT и MoQ отключены; публикация потоков через браузерный прокси не поддерживается. Внешняя служба сессий и новые зависимости не нужны.

## Развёртывание и миграция

1. Обновите/пересоберите приложение и пересоздайте **оба** Compose-сервиса с обновлённой конфигурацией. Обновление только образа приложения оставляет прежний открытый медиапорт уязвимым. Миграция камер, хранилищ и записей не нужна.
2. Для общей LAN задайте обе переменные аутентификации, `NVR_BIND=0.0.0.0`, а в bridge-режиме — LAN IP хоста в `WEBRTC_HOST`. С Linux LAN overlay оставьте `WEBRTC_HOST` пустым для обнаружения интерфейсов. Стандартная привязка — `127.0.0.1`; прежним LAN-установкам нужно изменить её явно. Пустые учётные данные допускают намеренно доверенную LAN и вызывают предупреждение при запуске.
3. Разрешите TCP приложения (по умолчанию 8080) и UDP WebRTC (8189). TCP 8889 больше не публикуется; `WEBRTC_PORT` сохранён в устаревшей конфигурации API, но не управляет браузерной сигнализацией. Не публикуйте TCP 8554/8889/9997, не подключайте недоверенные контейнеры к медиасети и не привязывайте службы MediaMTX в сети хоста к адресам вне loopback. Поставляемый Linux LAN overlay использует loopback; локальные процессы хоста доверенные. Внутренние слушатели MediaMTX не требуют входа: их сетевая изоляция — часть защиты.
4. При нативной установке закройте TCP endpoints MediaMTX через loopback или firewall. Задайте `MEDIAMTX_WEBRTC=http://127.0.0.1:8889` вместе с API/RTSP-настройками. Не проксируйте клиентам прямые endpoints MediaMTX.
5. HTTPS reverse proxy нужен только для origin приложения; он должен передавать методы `/api/media` и SDP content types. Сохраняйте внешний Host, передавайте доверенные заголовки схемы и задайте `COOKIE_SECURE=true`. В `FORWARDED_ALLOW_IPS` укажите реальные IP прокси; не доверяйте произвольным клиентским заголовкам и не используйте `*` для приложения, доступного напрямую. UDP по-прежнему требует соединения браузер–хост.
6. После обновления/перезапуска прежние cookie недействительны. Для смены пароля измените окружение и выполните `docker compose up -d --no-build --force-recreate nvr-app` с тем же образом и Compose-файлами. UI смены пароля нет. Запускайте один worker: сессии находятся в памяти процесса.

## Границы защиты

Служебные порты MediaMTX нельзя открывать напрямую. Скомпрометированный хост или контейнер в приватной сети имеет доступ к видео/API. Это граница развёртывания: FastAPI не защищает все слушатели MediaMTX. Один UDP-доступ без согласованной сигнализации не даёт просмотра.

HTTP в LAN может раскрыть пароль и cookie; вне доверенной LAN используйте HTTPS. Учётные данные в окружении/SQLite и записи не зашифрованы. Вход использует один общий аккаунт без ограничения перебора пароля: ограничьте сеть и выберите сильный пароль. Есть ограничения памяти для сессий и медиаресурсов. Неудачное удаление в gateway может задержать прекращение уже согласованного потока; отозванные cookie не позволяют новые запросы приложения. TLS/DTLS не защищают от скомпрометированного хоста или копирования видео авторизованным зрителем.

О приватном сообщении об уязвимостях см. [SECURITY.md](../SECURITY.md).
