# Архитектура

[Документация](README_RU.md) · [English](architecture.md)

```text
Browser: React UI
  ├── HTTP → FastAPI: configuration, diagnostics, archive metadata/files
  └── authenticated WHEP → FastAPI → private MediaMTX; negotiated WebRTC UDP → MediaMTX

Application (one Uvicorn worker)
  ├── SQLite: cameras, layouts, destinations, segment metadata, webhook queue
  ├── settings.json: installation timezone
  ├── MediaMTX API: managed main/substream RTSP paths
  ├── ffprobe: bounded direct camera checks and completed-file indexing
  └── FFmpeg recorder per active camera → original video copied into MP4 storage
```

`backend/main.py` отвечает за HTTP API с входом, жизненный цикл и согласование состояния. `db.py` инициализирует SQLite/WAL и выполняет предусмотренные обновления при запуске. В базе хранятся учётные данные камер; сериализаторы API скрывают приватные URL/пароли в общих ответах.

`video.py` управляет путями MediaMTX, кэшем и ограничением прямых проверок доступности, процессами FFmpeg, индексированием и очисткой по сроку. Запись не зависит от зрителей браузера. FFmpeg копирует видеодорожку без декодирования/перекодирования и имеет ограниченное время штатной остановки. Ровно один worker приложения должен владеть процессами.

`storage.py` проверяет назначения в ограниченных подпроцессах: запись/fsync, резерв места, необязательный `.nvr-storage-id` до создания каталогов записей. Приложение не монтирует файловые системы и не восстанавливает NAS. Недоступное защищённое хранилище блокирует свои recorders, не отключая другие назначения и прямой эфир.

`policies.py` вычисляет недельные окна записи в часовом поясе установки. `timeconfig.py` атомарно сохраняет пояс рядом с SQLite; абсолютные метки и имена файлов остаются UTC. Миграция базы для пояса не нужна.

`notifications.py` подавляет кратковременные сбои, сохраняет очередь SQLite, асинхронно доставляет вебхуки. Интеграций отдельных провайдеров и уведомления о полном отключении сервера нет.

`frontend/src/main.tsx` даёт навигацию, редактирование камер, Обзор и прямой мультиэкран. `Storage.tsx` отвечает за хранилища. `Archive.tsx` и `archiveClock.ts` поддерживают отдельный сеанс просмотра истории: одни монотонные абсолютные часы, независимые MP4 players, пакетные метаданные и коррекцию дрейфа 750 мс. `time.ts` форматирует местное время установки и привязывает отображение к серверному времени. Состояния live и архива раздельные.

Постоянные каталоги — `/data` (SQLite, WAL/SHM, настройки пояса) и `/recordings` (назначения и UTC-каталоги камеры/даты/часа). Пути MediaMTX восстанавливаются из конфигурации после перезапуска. См. [время и архив](time-and-archive_RU.md) и [решения релиза/развёртывания](releasing.md) (на английском).

## Передача и запись видео

```text
RTSP camera ── one upstream ── MediaMTX ── WebRTC/WHEP ── browser
                                 │
                                 └── local RTSP ── FFmpeg -c:v copy ── MP4 segments
```

Для дополнительного потока MediaMTX создаёт отдельный путь и подключается только при зрителях Multiview. Основной поток постоянно подключён, когда расписание разрешает запись и хранилище готово; иначе подключается по запросу. У каждого зрителя своя WebRTC-сессия, источник RTSP общий.

React использует официальный `reader.js` MediaMTX; см. [лицензию](../frontend/public/MEDIAMTX-LICENSE.txt). Плитки переключают `contain`/`cover` в браузере без масштабирования сервером. Раскладки Multiview сохраняются, поддерживают до 12 столбцов, перемещение и изменение размеров.

FFmpeg копирует видео без декодирования (`-c:v copy`), аудио не записывается. Каждый процесс принадлежит одному `ProcessSupervisor`, без shell interpolation. При штатной остановке FFmpeg получает SIGINT и до 15 секунд на завершение MP4, затем SIGKILL. Повторные запуски используют backoff до 60 секунд и jitter до секунды; работа более 30 секунд сбрасывает задержку до двух секунд. На границе каждого UTC-часа recorder штатно перезапускается. MediaMTX восстанавливает подключение к источнику независимо.

Каталоги и имена записей используют UTC:

```text
<storage>/<destination>/<camera_id>/YYYY/MM/DD/HH/YYYYMMDDTHHMMSS.mp4
```

Сегменты обычно около десяти минут; точные границы зависят от ключевых кадров. В архив попадают завершённые MP4, чья длительность проходит `ffprobe`; это не проверка целостности каждого кадра. Повреждённые неиндексированные файлы, включая MP4 без `moov` atom, остаются на диске для проверки; индексатор не ремонтирует и не удаляет их автоматически. FastAPI отдаёт видео и скачивание с HTTP byte ranges. Просмотр требует поддерживаемого браузером кодека.
