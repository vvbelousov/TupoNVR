# Хранилища, срок хранения и резервирование

[Документация](README_RU.md) · [English](storage.md)

## Хранение и очистка по сроку

`DEFAULT_RECORDING_PATH` в `.env` — **путь хоста**, подключённый к `/recordings` контейнера приложения. Это может быть локальный диск или уже смонтированный каталог NFS/SMB. Например:

```sh
sudo mount -t nfs nas:/export/nvr /srv/nvr
# Then set DEFAULT_RECORDING_PATH=/srv/nvr in .env.
```

`recording_destination` камеры — имя подкаталога, например `default` или `garage`; абсолютные пути и `..` запрещены. На хосте внутрь такого каталога можно смонтировать отдельную файловую систему. Монтирование, права записи и восстановление после перезагрузки настраиваются на хосте. Проверьте их до записи, включая поведение при недоступности NFS/SMB.

Срок хранения — семь дней по умолчанию, допустимы 1–3650 дней; пустое значение снимает ограничение по возрасту. Для записей удалённых камер действует семидневный предел от начала сегмента, а не от удаления камеры. Каждые пять минут worker индексирует записи и удаляет просроченные сегменты. При нехватке места удаляются старейшие индексированные файлы для достижения резерва `MIN_FREE_SPACE_GB` на соответствующей файловой системе. Текущий час активной камеры защищён. Если активные сегменты занимают всё место, резерв не гарантирован: рассчитывайте объём, задавайте срок хранения и следите за `/metrics`. Отсутствие ограничения по возрасту не отменяет удаление при нехватке места.

Сегменты можно удалять через API и [ручную очистку](recording-cleanup_RU.md). SQLite использует WAL; worker удаляет метаданные отсутствующих файлов. ID удалённых камер не используются повторно. При запуске существующие базы получают предусмотренные обновления схемы с сохранением строк, записей и раскладок.

## Защита каталогов назначения

Каждый каталог назначения отдельно проверяется на доступность, свободное место своей файловой системы, реальную временную запись/fsync и резерв `MIN_FREE_SPACE_GB`. При недоступности, отсутствии прав или нехватке места запись его камер останавливается и возобновляется после восстановления. Другие хранилища и прямой эфир работают. Проверки выполняются примерно каждые пять секунд в ограниченных подпроцессах с timeout три секунды. Устаревший статус не считается готовым. Метаданные недоступного хранилища не удаляются как отсутствующие файлы.

Включайте защиту внешнего ресурса **до включения записи камеры**:

1. Смонтируйте ресурс под `DEFAULT_RECORDING_PATH` на хосте, например `/srv/nvr/nas`. Настройте права и монтирование после перезагрузки.
2. В **Хранилище** выберите **Создать ID защиты**. Приложение создаёт случайный 256-битный ID, атомарно публикует `.nvr-storage-id` без перезаписи и проверяет чтение. Каталог уже должен существовать: операция не создаёт каталог вместо потерянного ресурса. Если отдельная точка монтирования не видна, создание требует подтверждения намеренно локального хранения. Не подтверждайте это для отсутствующего внешнего ресурса.
3. Если ID есть, выберите **Использовать существующий ID**. Несовпадение с ожидаемым требует явного подтверждения принятия ID подключённого ресурса. Создание не заменяет файл или настроенный ID. Повреждённый маркер исправьте вручную на нужном ресурсе. Без поддержки hard-link/fsync автоматическое создание не работает; остаётся ручной вариант.
4. **Ручная настройка:** создайте на ресурсе `.nvr-storage-id` из 1–128 символов (ASCII-буквы, цифры, `_`, `-`), сохраните ожидаемый ID. Изменение/отключение защиты требует подтверждения UI. `PUT /api/storage/destinations/nas` принимает `{"expected_marker":"nas-primary-01"}`. `POST /api/storage/destinations/{name}/protection` принимает `action` (`create`/`use_existing`), `previous_expected_marker` (включая null), `replace_existing`, `allow_local`. Операции только для настроенных назначений используют ограниченные подпроцессы, timeout три секунды, безопасные ошибки и защиту от symlinks/подмены каталога. Если ошибка возникла после записи маркера, он может остаться; проверьте ресурс и примите существующий ID.
5. Проверьте готовность, затем включите запись. Если назначения ещё нет в списке, зарегистрируйте его через API ручной настройки или добавьте камеру с отключённой записью и выбранным назначением.

При исчезновении ресурса или отсутствии/несовпадении ID приложение не создаёт защищённый каталог/ID и не начинает запись в нижележащий локальный каталог. `{"expected_marker":null}` отключает защиту. Обычные локальные назначения, включая `default`, сохраняют автоматическое создание каталогов.

ID проверяет идентичность, не является секретом и не заменяет монтирование ОС. Открытые дескрипторы остаются под управлением ОС после потери ресурса. NVR не гарантирует сохранность текущего сегмента и не исправляет зависший kernel I/O NFS/SMB. Для вложенных mounts настройте подходящие Compose bind mounts и проверьте видимость в контейнере; NVR не управляет mount propagation.

## Обновление, резервирование и восстановление

Сохраняйте `DATA_DIR`, `DEFAULT_RECORDING_PATH`, `.env` и настройки mounts хоста/NAS между обновлениями. Каталог данных включает SQLite, WAL/SHM при наличии, `settings.json` часового пояса; маркеры находятся в каталогах записей соответствующих назначений.

До обновления штатно остановите приложение командой `docker compose stop nvr-app` с теми же `-f` файлами установки. При остановленной записи резервируйте весь каталог данных, конфигурацию, записи и `.nvr-storage-id`. Защищайте копии как учётные данные камер. Не копируйте только активно изменяемый файл SQLite и не генерируйте новые ID при восстановлении. Автоматического резервирования/восстановления нет.

Для готового образа прочитайте release notes, выберите фиксированную версию `NVR_IMAGE`, выполните:

```sh
docker compose -f docker-compose.yml -f compose.image.yml pull
docker compose -f docker-compose.yml -f compose.image.yml up -d --no-build
```

Для LAN добавьте `-f compose.lan.yml` после основного файла в **обе** команды. Затем проверьте `/health`, `/ready`, хранилища и прогресс записи. Приложение обновляет базу при запуске. Старый образ может не поддерживать обновлённую базу; откат может требовать копию данных до обновления. Не удаляйте постоянные каталоги при пересоздании контейнеров.

Для восстановления держите приложение остановленным, восстановите полную соответствующую копию с нужным владельцем и mounts, выберите соответствующую версию и запустите. До записи проверьте ID и готовность. Испытайте резервирование на одноразовых данных; UI восстановления и автоматического отката миграций нет.
