# Сеть и WebRTC

[Документация](README_RU.md) · [English](networking.md)

## Выбор сетевого режима

| Режим | TCP приложения | TCP MediaMTX | UDP WebRTC | Кандидаты адресов |
|---|---|---|---|---|
| Основной `docker-compose.yml` (bridge) | Хост `NVR_BIND:NVR_PORT` → контейнер 8000 | 8554 / 8889 / 9997 в приватной сети `media`; не опубликованы | Хост `WEBRTC_UDP_PORT` (8189) | Пустой `WEBRTC_HOST` означает 127.0.0.1; для других устройств задайте LAN IP хоста |
| Основной + `compose.lan.yml` (сеть хоста Linux) | Хост `NVR_BIND:NVR_PORT` | Loopback хоста 8554 / 8889 / 9997 | Хост `WEBRTC_UDP_PORT` (8189) | Пустой `WEBRTC_HOST` включает штатное обнаружение интерфейсов хоста |

В обоих режимах приложение по умолчанию слушает localhost:8080. Для LAN нужны `NVR_BIND=0.0.0.0`, оба значения аутентификации и доступ доверенных зрителей к TCP приложения и UDP видео через firewall. Режим сети хоста требует Linux Engine, Compose 2.24.4+ и свободных TCP-портов медиаслужб. Оба контейнера могут обращаться к сетевым службам хоста; локальные процессы имеют доступ к endpoints MediaMTX на loopback без аутентификации. Bridge-режим доверяет участникам сети `media`. Не подключайте недоверенные контейнеры и не публикуйте TCP-порты MediaMTX.

Во всех командах используйте одинаковые аргументы `-f`; см. [установку](installation_RU.md). Перед сменой режима проверьте конфликты портов.

## Сигнализация и медиаданные

Браузер согласует WHEP через `/api/media` приложения; приложение передаёт сигнализацию приватному MediaMTX. Согласованный поток WebRTC UDP идёт напрямую между браузером и MediaMTX. `WEBRTC_PORT` — устаревшее значение API, а не опубликованный порт сигнализации. HLS, RTMP, SRT и MoQ отключены в поставляемой конфигурации.

Штатное обнаружение видит интерфейсы контейнера в bridge-режиме и хоста в LAN-режиме. Отдельная служба обнаружения, определение адреса по hostname браузера, переписывание SDP и обязательный STUN не используются. Объявленный ICE-кандидат не гарантирует доступ зрителя: проверьте маршрутизацию, VLAN и правила UDP firewall.

## VPN, NAT и HTTPS

Предпочитайте доступ только из LAN или через VPN публичному размещению NVR. Если автоматические кандидаты не подходят зрителям VPN, задайте доступные адреса в `WEBRTC_HOST` (IP или DNS-имена через запятую). VPN должен маршрутизировать TCP приложения и UDP видео.

HTTPS reverse proxy передаёт интерфейс, API, архив и сигнализацию WHEP, но не WebRTC UDP. Сохраняйте Host, передавайте OPTIONS/POST/PATCH/DELETE `/api/media` и типы содержимого SDP, задайте `COOKIE_SECURE=true`, настройте `FORWARDED_ALLOW_IPS` на реальные IP доверенного прокси. Прямые HTTP/API/RTSP MediaMTX держите закрытыми; см. [безопасность](security-hardening_RU.md).

Если прямое соединение для видео невозможно, настройте ICE/TURN MediaMTX в `mediamtx.yml`; TURN-сервис не поставляется и не обязателен для обычной LAN. MediaMTX также поддерживает `webrtcIPsFromInterfacesList`, `webrtcIPsFromInterfacesExcludeList` и отключение `webrtcIPsFromInterfaces` для использования только явных кандидатов. См. [справочник конфигурации MediaMTX](https://mediamtx.org/docs/references/configuration-file) для установленной версии. Если Проверить успешно, но прямой эфир не работает, см. [диагностику](troubleshooting_RU.md).
